# Hub-Spoke Stage 3A operations

Stage 3A identity, Hub/Spoke role, link, reconcile, origin, rate, and audit security state is network-scoped on multisite. Existing source registry and defaults configuration remains per-blog and is neither migrated nor merged; pre-accept credential inventory explicitly visits every blog. An installation cannot be both a Hub and an active Spoke. Any nonempty role, reconciliation, or unresolved acceptance state blocks a new Hub invitation or Spoke role transition until durable cleanup completes.

The feature flag defaults off for authority-increasing actions. While it is off, password reauthentication can issue a five-minute session-bound cleanup-only proof. That proof is accepted only by revoke, unlink, cancellation, and recovery permissions and is rejected by create, accept, rotate, provision, credential-write, and proxy expansion paths. Disabling the flag does not disable authenticated remote revoke, local credential wipe, source disable, audit, cron reconciliation, or the explicit uncertain-accept cleanup flow.

Credentials are accepted only in the route-specific `Authorization` header. They are never accepted in query parameters, cookies, or rotation JSON bodies. Active Spoke state blocks new or replacement upstream, source, Bridge Server, vendor, and marketplace credentials on every blog; credential deletion remains available.

Lifecycle audit rows store opaque resource hashes, bounded reason classification, optional reason hashes, and actor classification without raw credentials. All append operations share one network advisory lock and retain the newest 500 rows. Expiry persists invitation state and then atomically appends one audit batch containing one row per invitation; audit failure rolls invitation state back without overwriting concurrent audit rows. Cleanup success is audited only after source and role cleanup persist.

Reconciliation workers claim due rows under the network reconcile lock, release the lock before outbound HTTP or local cleanup, and commit each result only when its claim still matches. Concurrent enqueues therefore remain durable and stale claims become retryable after five minutes. A caller that cannot persist a required reconcile row receives `503`; it is never told that reconciliation is pending when no durable row exists.

Remote-revoke receipts contain only the hash of the credential actually presented and are scoped to the same revoked link and compensation route. They remain with the revoked link so a lost `204` can be retried after an extended outage; they never authorize proxy routes.
